# First release of etoro-trading-mcp v1.0.0 (release notes + CI-driven publish)

## Goal

**Intended outcome.** Publish the first public release of `etoro-trading-mcp` as **v1.0.0**: npm package published with provenance, a GitHub release carrying accurate generated release notes, cut and published exclusively through the existing tag-driven CI release workflow.

**Observable success criteria.**

1. `npm view etoro-trading-mcp@1.0.0` returns published metadata (with provenance), and `npx -y etoro-trading-mcp@1.0.0` is installable.
2. GitHub release `v1.0.0` exists, published (not draft), with the tarball and notes generated by `npm run release:notes` from the finalized changelog.
3. The Release workflow's **verify** and **publish** jobs both succeeded for tag `v1.0.0`; no local `npm publish` was ever run.
4. CI stays green on `main` for the release commit before tagging.

**Scope.**

- **Changelog finalization (the "release notes" work):** fold the current `[Unreleased]` section — the two allowlist breaking changes — **into `[1.0.0]`**, and rewrite the stale `[1.0.0]` claims ("Safe default exposure of 28 current tools", implied enable/disable controls) to describe allowlist-only exposure. Rationale: v1.0.0 has never been tagged or published (no git tags; npm name returns 404), so nothing can break; the shipped code *is* the allowlist behavior. Set the section date to the actual tagging day.
- **Small accuracy fix:** update `package.json` `description` ("…demo-safe defaults" → allowlist-accurate phrasing). `check-package.ts` doesn't assert the description, so this is safe.
- **One-time release setup (the "CI" work), per MAINTAINERS.md:** create GitHub Environment `production` (no required reviewers — solo maintainer); user adds an npm **Automation** token as the `NPM_TOKEN` secret in that environment; enable branch protection on `main` (require the 6 CI matrix checks, forbid force pushes and deletion, administrators excluded so the solo maintainer can still land direct hotfixes).
- **Cut the release:** land the changelog/description commit on `main`, wait for green CI, run the local pre-flight (`npm run release:validate -- v1.0.0`, which includes the full `npm run verify` suite, plus a preview of `npm run release:notes`), then tag `v1.0.0` on the merged `main` HEAD and push only the tag. Watch the Release workflow through npm publish, `publication:verify`, and release publishing.

**Non-goals.** No workflow/code changes beyond the changelog and package description; no version bump beyond 1.0.0; no announcement/marketing; no changes to the Swagger-sync automation; no npm-side provenance setup (already configured via public repo + `id-token: write`).

**Constraints, assumptions, decisions.**

- The workflow is the only publish path; local `npm publish` and feature-branch releases are forbidden (repo rule, enforced by convention).
- `gh` is authenticated as `n-kostadinov` with **admin** on the repo, so environment creation, secret setting (if chosen), and branch protection can be executed via `gh api` / `gh secret set`.
- **NPM_TOKEN handling (default):** the maintainer creates the Automation token on npmjs.com (publish rights limited to `etoro-trading-mcp`; account 2FA must permit automation tokens) and pastes it into _Settings → Environments → production → secrets_ directly, so the secret never transits the agent chat. Alternative: supply it to the implementer for `gh secret set NPM_TOKEN --env production`.
- Local `main` is 5 commits behind `origin/main` (PR #1 merge) — first step fast-forwards it; the release is cut from origin/main HEAD `837ce6e` + the changelog commit.
- `release:validate` hard-gates: tag/version/lockfile match, dated changelog section without placeholders, npm-registry freshness (currently 404 = free), and `origin/main` ancestry — all satisfied by this plan.

**Key research findings.** CI (`ci.yml`, 3 OS × Node 22/24 running `npm run verify`) is already green on main; `release.yml` already implements verify → draft-release → npm publish with provenance → publish; PR #1 already updated the notes builder, catalog, README, and docs for allowlist-only defaults — the changelog's 1.0.0 section is the single stale release artifact; the npm package name is unclaimed; no GitHub environments exist yet (the publish job requires `production`).

**Testing stance.** No new unit or integration tests are authored for this goal; it is release operations plus a changelog/description text change. The existing verify suite and CI jobs are the proof at every gate.

## Execution notes

- **Task 1:** commit `629fc7e` ("docs(release): fold allowlist changes into the 1.0.0 changelog") landed on `main`; CI run `40238387735` succeeded. The plan file itself was force-added to the commit (`.gitignore` ignores `plan/`, but PR #1 set the convention of committing release plans; `check-package.ts` excludes `plan/` from the tarball regardless).
- **Task 2:** branch protection applied and verified (six `Verify (…)` contexts required, `enforce_admins` false, force pushes and deletions denied). The environment-creation API rejected the `deployment_branch_policy` payload (422: `custom_branch_policies` and `protected_branches` cannot both be false) — the environment was still created, and having **no** branch policy is the correct end state, because deployment branch policies can block tag-triggered jobs and the publish job runs from a tag push. Verified: `production` exists, no branch policy, no protection rules (no required reviewers).
- **Task 3 (blocker):** requires the maintainer's npm Automation token, which only the maintainer can create. `gh secret list --env production` is empty. Until `NPM_TOKEN` exists, tasks 5 and 6 cannot run (the publish job would fail at the npm publish step).
- **Task 3 (resolved):** first attempt landed as a repository-level secret; after the maintainer added `NPM_TOKEN` to the `production` environment, the repository-level copy was deleted via `gh secret delete`, leaving the environment-scoped secret as the only one.
- **Task 4:** `npm run release:validate -- v1.0.0` printed `"valid": true` for commit `629fc7e` (== `origin/main`), with all eleven checks green locally. Transient Windows EPERM on `node_modules/@esbuild/win32-x64/esbuild.exe` broke the first `npm ci` attempt inside the validator (stale file lock, no esbuild process afterwards); a direct `npm ci` succeeded and the rerun validated cleanly. Release-notes preview at `artifacts/release-notes-v1.0.0.md` (gitignored) confirms allowlist-only exposure wording, v1.400.0 baseline, 197 operations / 27 toolsets, and the "first tagged release" comparison line.
- **Task 5:** annotated tag `v1.0.0` pushed for commit `629fc7e` (tag object `12cb498b`); Release run `40273135482` started from the tag push.
- **Task 6 (retry pending):** the verify job passed, but `npm publish` failed with 403: "Two-factor authentication or granular access token with bypass 2fa enabled is required to publish packages" — the supplied token type cannot publish while the npm account enforces 2FA for writes. npm remained unpublished (registry 404), and the leftover draft GitHub release was deleted per MAINTAINERS.md. Fix: create a classic **Automation** token on npmjs.com, overwrite `NPM_TOKEN` in the `production` environment, then re-run the failed publish job of run `40273135482` (`gh run rerun 40273135482 --failed`).
- **Task 6 (completed):** after the maintainer replaced the token with a classic Automation token, `gh run rerun 40273135482 --failed` published to npm successfully (with provenance), but the metadata-verification step failed because npm held the brand-new package in staged publishing (`0.0.0-stage` placeholder under maintainer `machine-minds-ltd`) past the verifier's 30-second polling window. Staging cleared within minutes: registry lists 1.0.0, `dist-tags.latest` = 1.0.0, and `dist.attestations.provenance` (SLSA v1) is present (the verifier's `provenanceAttestation: false` is an `npm view` field-visibility artifact, disproven by the raw packument). Per MAINTAINERS.md's "publish succeeded but a later step failed" procedure, the equivalent verification was run locally (`publication:verify` → `"published": true`) and the leftover draft was flipped manually (`gh release edit v1.0.0 --draft=false`). End-to-end proof: a clean `npm install etoro-trading-mcp@1.0.0` in a temp directory runs `cli.js tools list` → "Enabled tools: 0 of 197 catalog operations" (allowlist defaults).
